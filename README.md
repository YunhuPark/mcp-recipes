# MCP 레시피

한국어, 직무별, **결과 중심**의 AI 도구(MCP) 조합 레시피를 모으는 프로젝트입니다. 마케터부터 시작합니다.

## 지금 단계

**코드와 사이트 없이, 직접 검증한 레시피를 콘텐츠로 공개해 수요를 확인하는 단계**입니다.
설치 자동화나 사이트는 수요가 확인된 뒤에 검토합니다. (이른 투자 금지)

## 핵심 원칙

1. **직접 돌려본 것만 "됐다"고 쓴다.** 실패, 막힌 곳, 미검증 항목을 문서에 그대로 적는다.
2. **"클릭 한 번"을 약속하지 않는다.** 연결과 로그인, 검수 단계를 솔직하게 적는다.
3. **외부에 영향을 주는 작업은 먼저 확인한다.** 게시, 삭제, 개인 캘린더나 계정 변경은 승인 후에만.
4. **테스트 흔적은 목록으로 남기고 정리한다.** (`validation-log.md`의 "남아 있는 테스트 흔적")
5. 저작권이 있는 원문은 저장하지 않고 분석과 요약만 기록한다.

## 계속할지 정하는 기준

**기준 확정일: 2026-10-13** (첫 글을 올리기 전에 정했다. **첫 글을 올린 뒤에는 바꾸지 않는다.**)

**수정 이력**
- 2026-10-12: 최초 설정. 계속 15건 이상 / 조정 5~14건 / 접기 검토 5건 미만.
- 2026-10-13: **첫 글 게시 전에** 수정. 계속 5건 이상 / 조정 2~4건 / 접기 검토 2건 미만. 사유: 글을 올릴 Threads 계정의 팔로워가 14명(2026-10-13 기준)이라, 서로 다른 사람 15명의 요청은 팔로워 전원이 요청해도 닿을 수 없는 값이었다. 결과를 보고 바꾼 것이 아니다.

### 일정

| 항목 | 값 |
|---|---|
| 준비 완료(버퍼 7개 검수) | 2026-10-13 |
| 첫 게시 | **2026-10-14** |
| 게시 빈도 | 하루 1개 (단독 글 중심, 스레드는 주 1~2개 사이에 섞음) |
| 기간 | 4주 (2026-10-14 ~ 2026-11-10, 글 28개) |
| 주간 집계일 | 10/20, 10/27, 11/3, 11/10 |
| 최종 판단일 | **2026-11-11** |

### 세는 방식

- 지표는 **"레시피 요청"** 이다. 댓글이나 DM으로 "보내주세요", "내 직무 조합도 알려주세요"처럼 요청한 사람 수.
- **서로 다른 사람**만 센다. 같은 사람의 중복, 본인, 지인은 제외한다.
- 조회, 좋아요, 저장, 공유는 **기록은 하되 판단 기준으로 쓰지 않는다.** (수요의 증거가 못 된다.)
- 신청 폼이 아직 없어서 대기자 수는 기준에서 제외한다. 요청이 2건 이상 쌓이면 폼을 만들고, 그때부터는 대기자 수를 보조 지표로 추가한다.
- **팔로워 수는 보조로 기록한다.** (시작 시점 14명, 2026-10-13.) 판단 기준은 아니고 추이만 본다. 계정이 작아서 요청이 적더라도 팔로워가 꾸준히 늘면 다른 의미의 신호일 수 있다.

### 판단 기준 (임의로 정한 값, 업계 벤치마크 아님)

| 결과 | 조건 (4주 동안 서로 다른 사람의 요청) | 다음 행동 |
|---|---|---|
| **계속** | **5건 이상** | 요청이 몰린 직군과 도구를 다음 레시피로 선정 |
| **조정** | 2~4건 | 반응이 컸던 소재와 문구를 살려 **한 번 더 4주** 진행 |
| **접기 검토** | 2건 미만 | 형태를 바꿀지(예: 소재, 채널, 글 형식) 별도로 판단 |

- 이 값은 **팔로워 14명이라는 규모를 보고 정했다.** 팔로워가 크게 늘어도 중간에 바꾸지 않고, 끝난 뒤에 "이 규모에서의 기준이었다"고 해석한다.

- 반응이 한 글에만 몰리면 "레시피 전체"가 아니라 "그 소재"의 수요로 해석한다.
- 요청은 **관심**이지 구매 의사가 아니다. 돈을 낼지는 별개로 검증한다.
- 결과가 나빠도 "수요 없음"이 아니라 "이 채널과 이 문구에서 반응 없음"일 수 있다. 그래서 접기 전에 조정 기회를 한 번 둔다.

### 운영 규칙

- **글 7개를 미리 검수해 둔 상태를 유지한다.** (버퍼가 3개 아래로 내려가면 새 글 작성과 검증을 우선한다.)
- 매주 **새 레시피를 1개씩 검증**해서 글감을 확보한다. 검증하지 않은 내용으로 글 수를 채우지 않는다.
- 게시는 **단계적으로 자동화**한다 (2026-10-14 결정). 처음 3개는 사람이 미리보기를 확인하고 명령 한 줄로 올리고, 그 3개가 성공한 뒤에만 예약 실행으로 넘어간다. 올라가는 글은 `검수완료`이고 점검을 통과한 글뿐이다. 설계와 안전 장치는 `docs/auto-post.md`.
- 올리기 전 체크: 사실 확인, 오타, 과장 표현, 미검증 항목 표기 (`posts/schedule.md`의 글별 체크리스트)
- 진행 현황: `python scripts/status.py` 로 게시 수, 버퍼, 성공 기준 진행도, 다음 집계일, 글감 여유를 한 화면에서 본다. 파일을 읽기만 하고, 집계 숫자만 다룬다. 판단 기준은 이 README의 표를 읽는다.
- 자동 점검: `python scripts/check.py` 로 글자 수(500자), 비밀값과 개인 정보 패턴, 브랜드명 철자, 일정표와 글 상태의 일치, 푸시하지 않은 커밋의 작성자와 메시지를 확인한다. **패턴 기반이라 완전하지 않고 사실 확인은 하지 못한다.** 개인 키워드는 저장소에 올라가지 않는 로컬 파일(`.check-blocklist.local`)에 둔다.

## 알려진 위험 (냉정한 평가에서)

- 시장이 작을 수 있음 (한국어 + 마케터 + MCP를 실제로 쓰는 사람)
- 레시피는 복제하기 쉬움
- 큰 플랫폼의 직무별 플러그인이 흡수할 수 있음
- 도구와 MCP가 바뀌어 레시피가 빨리 낡음 → 날짜와 검증 환경을 항상 기록
