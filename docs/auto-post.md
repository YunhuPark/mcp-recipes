# Threads 게시 자동화 (단계적)

> 상태: **읽기 전용 호출(토큰 확인, 지표 읽기)은 2026-10-20에 실제로 성공했고, 글을 올리는 호출은 아직 한 번도 하지 않았다.** 아래 "검증한 것 / 못 한 것"을 먼저 읽는다.

2026-10-14에 "게시는 직접 한다"는 규칙을 바꿨다. 다만 한 번에 전부 맡기지 않고 단계를 둔다.

| 단계 | 방식 | 넘어가는 조건 |
|---|---|---|
| 0 | 사람이 직접 올린다 (도구 준비 전) | 토큰과 도구가 준비됨 |
| 1 | 도구가 미리보기를 보여주고, 사람이 `yes`를 입력해 올린다 | 이 방식으로 **3번 성공** |
| 2 | 작업 스케줄러가 매일 정해진 시간에 오늘 날짜의 글을 올린다 | - |

3번 성공 전에는 `--scheduled`가 열리지 않는다 (코드로 막혀 있다).

## 쓰는 법

```bash
python scripts/post.py D02                  # 미리보기. 네트워크 호출 없음
python scripts/post.py D02 --publish        # 실제 발행. THREADS_LIVE=yes 가 있어야 하고, 마지막에 yes 를 입력
python scripts/post.py --status             # 발행 기록과 토큰 만료 경고
python scripts/post.py --check-token        # 토큰이 유효한지 읽기 전용으로 확인 (아무것도 게시하지 않음)
python scripts/insights.py                  # 게시한 글의 조회와 반응을 표로 (읽기 전용, threads_manage_insights 권한 필요)
```

실패했을 때:

- 글이 만들어지기 전에 **분명히 실패**했으면 `--retry --publish`로 다시 시도할 수 있다.
- 발행 단계에서 응답이 없거나 이상하면 **불확실**로 기록하고 멈춘다. 자동으로 다시 하지 않는다. Threads에서 실제로 올라갔는지 눈으로 확인한 뒤 `--resolve published` 또는 `--resolve not_published`로 정리한다. 불확실한 글이 하나라도 있으면 다른 글도 올라가지 않는다.

## 안전 장치 (이유 포함)

| 장치 | 이유 |
|---|---|
| 기본은 드라이런, 발행에는 `--publish` + `THREADS_LIVE=yes` 둘 다 필요 | 명령을 잘못 쳐도, 환경이 잘못 남아 있어도 혼자서는 올라가지 않게 |
| `검수완료`인 글만, 글 파일과 일정표 둘 다 | 검수 안 된 글이 올라가는 것을 막음 |
| 올리기 직전 `check.py` 통과 필수 | 비밀값, 개인 정보 패턴, 글자 수, **근거표**(인용이 근거 파일에 있는지, 대조 뒤 본문이 바뀌지 않았는지) |
| API 호출 **전에** 시도 기록을 디스크에 남김 | 중간에 죽어도 "시도했는지"를 알 수 있게 |
| 불확실하면 자동 재시도 금지 | 이미 올라간 글을 한 번 더 올리는 사고를 막음 |
| 같은 글 두 번 금지, 하루 1개 | 중복 게시, 폭주 방지 |
| 토큰 대체 금지 (`THREADS_ACCESS_TOKEN`만 사용) | 다른 서비스 토큰으로 엉뚱한 곳에 올리는 것을 막음 |
| 토큰은 환경 변수로만, 출력과 기록에 남기지 않음 | 기록 파일과 로그로 새지 않게 |
| 글자 수는 이모지를 UTF-8 바이트로 세어 500 제한 검사 | API 문서의 계산 방식에 맞춤 (보수적으로 셈) |
| 발행 확인은 사람의 `yes` (1단계) | 마지막 눈 |

기록 파일(`.post-state.local.json`)과 `.env*`는 `.gitignore`에 들어 있어 저장소에 올라가지 않는다.

- 안전 장치를 일부러 망가뜨려 보고(발행 14가지, 읽기 전용 호출 9가지), 시험이 모두 실패로 잡는지 확인했다 (시험이 정말로 막고 있는지 보려는 것).
- `--check-token`과 `insights.py`는 읽기만 한다 (GET만 쓰고, 게시 호출이 없는 것을 시험으로 확인).
- **2026-10-20 실제 Threads에서 성공:** 토큰 확인(`--check-token`: 토큰이 유효하고 `THREADS_USER_ID`와 같은 계정), 토큰 저장(`get_token.py --from-token`), 지표 읽기(`insights.py`로 D04 조회 98 등).
- 실제 저장소에서 미리보기가 네트워크 호출 없이 동작하고, 토큰이 없으면 발행이 거절된다.

**검증하지 못함**
- 토큰 발급 도우미(`get_token.py`)의 실제 동작. 가짜 통신으로 시험 21개를 통과했고 비밀값을 출력하지 않는 것도 확인했지만, 실제 Threads와는 연결해 보지 않았다.
- **글을 올리는 실제 호출**(컨테이너 만들기, 발행). 요청 형식은 공식 문서를 근거로 했고 실제 응답으로는 확인하지 않았다. **1단계 첫 글이 첫 실제 게시 시험이다.**
- 도구로 올린 글에 "AI Threads" 커뮤니티 표시가 붙는지 (지정하는 옵션은 확인하지 못함).
- `insights.py`의 일부 값. 2026-10-20 첫 실행에서 조회, 좋아요, 답글, 리포스트가 읽혔지만(조회 수는 계정 화면의 값과 맞는 것을 D04로 확인), 일부 글과 지표는 `-`(읽지 못함)로 나왔다. 이유는 아직 모른다.
- 컨테이너 생성 후 대기 시간 30초가 충분한지.
- 이모지 계산이 API의 실제 판정과 정확히 같은지 (보수적으로 크게 세므로 한도 초과는 막지만, 멀쩡한 글을 막을 수는 있다).
- 작업 스케줄러에서의 실행 (2단계 전에 따로 시험).
- 토큰 갱신 흐름. 장기 토큰은 60일이 지나면 만료되고, 만료 전에 갱신해야 한다.

## 준비 (사람이 직접 해야 하는 것)

토큰과 계정 설정은 도구가 대신 하지 않는다. 토큰을 채팅이나 저장소에 붙여넣지 않는다.

**자세한 순서와 막히는 곳은 `docs/token-guide.md`.** 토큰은 `python scripts/get_token.py`(사용자가 본인 터미널에서 실행)로 발급하고 환경 변수에 저장할 수 있다. 아래는 요약이다.

1. Meta 개발자 사이트에서 앱을 만들고 Threads API 사용을 추가한다.
2. 앱 권한: `threads_basic`, `threads_content_publish` (지표를 보려면 `threads_manage_insights`).
3. 본인 Threads 계정을 앱의 테스터로 추가하고 수락한다.
4. 단기 토큰을 받고 **장기 토큰(60일)** 으로 교환한다.
5. 환경 변수 (이 PC의 사용자 환경 변수에 저장):

   | 이름 | 내용 |
   |---|---|
   | `THREADS_ACCESS_TOKEN` | 장기 토큰 |
   | `THREADS_USER_ID` | Threads 사용자 ID (숫자) |
   | `THREADS_TOKEN_EXPIRES` | 토큰 만료일 `YYYY-MM-DD` (만료가 가까우면 `--status`가 경고) |
   | `THREADS_LIVE` | 실제 발행할 때만 `yes`. 평소에는 비워 둔다 |

6. 장기 토큰 갱신은 만료 전, 발급 24시간 뒤부터 가능하다. 갱신하면 `THREADS_TOKEN_EXPIRES`도 고친다.
7. 환경 변수를 넣은 뒤 `python scripts/post.py --check-token`으로 토큰과 계정이 맞는지 먼저 확인한다 (읽기 전용).
8. 2단계(스케줄러)는 1단계에서 3번 성공한 뒤에 설정한다.

## 다음 순서

| 순서 | 할 일 | 누가 |
|---|---|---|
| 1 | Meta 앱, 테스터 수락, 장기 토큰, 환경 변수 (위 준비 1~6) | 사용자 |

| 3 | 첫 3개 글을 `--publish`로 올림 (미리보기 확인, `yes` 입력). 이때 **글마다 올라간 모양을 직접 확인** | 사용자 |
| 4 | `insights.py`로 조회 수를 읽어 `게시 후 기록`에 반영 | Claude |
| 5 | 스케줄러 등록 (아래) | 사용자가 승인하고 등록 |

## 스케줄러 등록 (3번 성공한 뒤에만, 아직 하지 않음)

작업 스케줄러는 PC의 설정을 바꾸는 일이라 Claude가 임의로 등록하지 않는다. 등록할 때의 기준:

- 매일 정해진 시각에 `python scripts\post.py --scheduled --publish`를 실행한다. 오늘 날짜의 `검수완료` 글만 올리고, 없으면 아무것도 하지 않는다.
- `THREADS_LIVE=yes`는 평소 환경에 두지 않고, 작업의 실행 명령에서만 설정한다 (예: `cmd /c "set THREADS_LIVE=yes&& python scripts\post.py --scheduled --publish"`). 저장소 폴더에서 실행해야 한다.
- 토큰은 사용자 환경 변수에서 읽는다. 작업 설정 안에 적지 않는다.
- PC가 꺼져 있으면 그날은 올라가지 않는다. 늦게 켜져서 실행되더라도 오늘 날짜의 글만 고른다. 어긋나면 `--status`로 확인한다.
- 실패하거나 불확실하면 자동으로 다시 하지 않는다 (위 안전 장치). 다음 날 사람이 `--status`로 보고 정리한다.
- **사람의 확인을 줄이는 방법**은 글을 쓰는 단계를 일주일 단위로 묶는 것이다. 월요일에 그 주 글 7개를 `검수완료`로 확정하면, 스케줄러는 확정된 글만 올린다.

## 한계

- 이 도구는 글을 올릴 뿐이다. 글의 사실 여부와 말투는 `검수완료` 단계에서 사람이 본다.
- 올라간 뒤 지표는 `insights.py`로 읽을 수 있지만(토큰이 있을 때), 요청으로 센다고 판단하는 일(댓글이 직무나 도구를 구체적으로 적은 요청인지)은 사람이나 Claude가 읽고 정한다.
- **자동화는 글을 만들어 주지 않는다.** 새 글감은 새로 검증해야 생기므로, 병목은 올리는 일이 아니라 검증하는 일이다.
- 스케줄러로 넘어가면 사람의 마지막 확인이 사라진다. 그래서 3번의 수동 성공과 하루 1개 제한, 불확실 시 정지를 둔다.
