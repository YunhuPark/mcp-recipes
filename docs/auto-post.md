# Threads 게시 자동화 (단계적)

> 상태: **도구는 만들고 시험했지만, 실제 Threads API는 아직 한 번도 호출하지 않았다.** 아래 "검증한 것 / 못 한 것"을 먼저 읽는다.

2026-10-14에 "게시는 직접 한다"는 규칙을 바꿨다. 다만 한 번에 전부 맡기지 않고 단계를 둔다.

| 단계 | 방식 | 넘어가는 조건 |
|---|---|---|
| 0 | 사람이 직접 올린다 (도구 준비 전) | 토큰과 도구가 준비됨 |
| 1 | 도구가 미리보기를 보여주고, 사람이 `yes`를 입력해 올린다 | 이 방식으로 **3번 성공** |
| 2 | 작업 스케줄러가 매일 정해진 시간에 오늘 날짜의 글을 올린다 | - |

3번 성공 전에는 `--scheduled`가 열리지 않는다 (코드로 막혀 있다).

## 쓰는 법

```bash
python scripts/post.py D02                  # 미리보기. 네트워크 호출 없음
python scripts/post.py D02 --publish        # 실제 발행. THREADS_LIVE=yes 가 있어야 하고, 마지막에 yes 를 입력
python scripts/post.py --status             # 발행 기록과 토큰 만료 경고
```

실패했을 때:

- 글이 만들어지기 전에 **분명히 실패**했으면 `--retry --publish`로 다시 시도할 수 있다.
- 발행 단계에서 응답이 없거나 이상하면 **불확실**로 기록하고 멈춘다. 자동으로 다시 하지 않는다. Threads에서 실제로 올라갔는지 눈으로 확인한 뒤 `--resolve published` 또는 `--resolve not_published`로 정리한다. 불확실한 글이 하나라도 있으면 다른 글도 올라가지 않는다.

## 안전 장치 (이유 포함)

| 장치 | 이유 |
|---|---|
| 기본은 드라이런, 발행에는 `--publish` + `THREADS_LIVE=yes` 둘 다 필요 | 명령을 잘못 쳐도, 환경이 잘못 남아 있어도 혼자서는 올라가지 않게 |
| `검수완료`인 글만, 글 파일과 일정표 둘 다 | 검수 안 된 글이 올라가는 것을 막음 |
| 올리기 직전 `check.py` 통과 필수 | 비밀값, 개인 정보 패턴, 글자 수, **근거표**(인용이 근거 파일에 있는지, 대조 뒤 본문이 바뀌지 않았는지) |
| API 호출 **전에** 시도 기록을 디스크에 남김 | 중간에 죽어도 "시도했는지"를 알 수 있게 |
| 불확실하면 자동 재시도 금지 | 이미 올라간 글을 한 번 더 올리는 사고를 막음 |
| 같은 글 두 번 금지, 하루 1개 | 중복 게시, 폭주 방지 |
| 토큰 대체 금지 (`THREADS_ACCESS_TOKEN`만 사용) | 다른 서비스 토큰으로 엉뚱한 곳에 올리는 것을 막음 |
| 토큰은 환경 변수로만, 출력과 기록에 남기지 않음 | 기록 파일과 로그로 새지 않게 |
| 글자 수는 이모지를 UTF-8 바이트로 세어 500 제한 검사 | API 문서의 계산 방식에 맞춤 (보수적으로 셈) |
| 발행 확인은 사람의 `yes` (1단계) | 마지막 눈 |

기록 파일(`.post-state.local.json`)과 `.env*`는 `.gitignore`에 들어 있어 저장소에 올라가지 않는다.

## 검증한 것 / 못 한 것

**검증함**
- 가짜 통신 계층으로 시험 25개 통과 (`python -m unittest scripts/test_post.py`).
- 안전 장치를 일부러 14가지 망가뜨려 보고, 시험이 모두 실패로 잡는지 확인했다 (시험이 정말로 막고 있는지 보려는 것).
- 실제 저장소에서 미리보기가 네트워크 호출 없이 동작하고, 토큰이 없으면 발행이 거절된다.

**검증하지 못함**
- 실제 Threads API 호출. 요청 형식은 공식 문서를 근거로 했지만 실제 응답으로는 확인하지 않았다. **1단계 첫 글이 사실상 첫 실제 시험이다.**
- 컨테이너 생성 후 대기 시간 30초가 충분한지.
- 이모지 계산이 API의 실제 판정과 정확히 같은지 (보수적으로 크게 세므로 한도 초과는 막지만, 멀쩡한 글을 막을 수는 있다).
- 작업 스케줄러에서의 실행 (2단계 전에 따로 시험).
- 토큰 갱신 흐름. 장기 토큰은 60일이 지나면 만료되고, 만료 전에 갱신해야 한다.

## 준비 (사람이 직접 해야 하는 것)

토큰과 계정 설정은 도구가 대신 하지 않는다. 토큰을 채팅이나 저장소에 붙여넣지 않는다.

1. Meta 개발자 사이트에서 앱을 만들고 Threads API 사용을 추가한다.
2. 앱 권한: `threads_basic`, `threads_content_publish` (지표를 보려면 `threads_manage_insights`).
3. 본인 Threads 계정을 앱의 테스터로 추가하고 수락한다.
4. 단기 토큰을 받고 **장기 토큰(60일)** 으로 교환한다.
5. 환경 변수 (이 PC의 사용자 환경 변수에 저장):

   | 이름 | 내용 |
   |---|---|
   | `THREADS_ACCESS_TOKEN` | 장기 토큰 |
   | `THREADS_USER_ID` | Threads 사용자 ID (숫자) |
   | `THREADS_TOKEN_EXPIRES` | 토큰 만료일 `YYYY-MM-DD` (만료가 가까우면 `--status`가 경고) |
   | `THREADS_LIVE` | 실제 발행할 때만 `yes`. 평소에는 비워 둔다 |

6. 장기 토큰 갱신은 만료 전, 발급 24시간 뒤부터 가능하다. 갱신하면 `THREADS_TOKEN_EXPIRES`도 고친다.
7. 2단계(스케줄러)는 1단계에서 3번 성공한 뒤에 설정한다.

## 한계

- 이 도구는 글을 올릴 뿐이다. 글의 사실 여부와 말투는 `검수완료` 단계에서 사람이 본다.
- 올라간 뒤 지표(조회, 요청 수)는 여전히 사람이 `게시 후 기록`에 적는다.
- 스케줄러로 넘어가면 사람의 마지막 확인이 사라진다. 그래서 3번의 수동 성공과 하루 1개 제한, 불확실 시 정지를 둔다.
